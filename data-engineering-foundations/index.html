Chapter 2

What is Data Engineering?

Data engineers build the platforms and pipelines that collect, store, transform, and serve data. They sit between the systems that produce data (applications, sensors, logs) and the people who consume it (analysts, data scientists, business stakeholders).

Data Engineering

Builds reliable data infrastructure, pipelines, and storage. Focuses on availability, scale, and quality.

Data Science

Builds models, experiments, and predictions on data prepared by engineers. See also Machine Learning with Python.

Data Analytics

Answers business questions with dashboards, reports, and ad-hoc queries.

Typical responsibilities

  • Ingest data from APIs, databases, files, message queues, and streaming sources.
  • Design schemas, warehouses, and data marts.
  • Build batch and streaming ETL/ELT pipelines.
  • Ensure data quality, lineage, security, and governance.
  • Monitor, optimize, and scale data infrastructure.

Key mindset

Data engineering is infrastructure engineering for data. Reliability, observability, and reproducibility matter as much as volume and speed.

Chapter 3

Data Sources & Generation

Before moving data, you must understand where it comes from and how it is generated. Data sources shape collection frequency, schema, quality, and legal constraints.

Structured sources

  • Relational databases (OLTP) such as PostgreSQL and MySQL.
  • Data warehouses and data marts.
  • Spreadsheets and CSV exports.

Semi/unstructured sources

  • JSON from REST APIs and webhooks.
  • Log files, clickstream events, and sensor telemetry.
  • Images, documents, audio, and video.
{
  "event_id": "evt_42",
  "user_id": "usr_998",
  "event_type": "page_view",
  "page": "/pricing",
  "timestamp": "2024-09-12T14:35:00Z",
  "metadata": {
    "browser": "Firefox",
    "device": "mobile"
  }
}

Collection considerations

  • Frequency: batch hourly/daily vs near-real-time streaming.
  • Schema: fixed columns vs evolving JSON documents.
  • Volume: thousands vs billions of events per day.
  • Quality: duplicates, missing values, out-of-order timestamps.
  • Legal/ethical: consent, PII, retention, and jurisdiction.

Chapter 4

Data Modeling Basics

Data modeling turns real-world concepts into tables, columns, and relationships. Good models make queries fast, joins simple, and updates safe. This chapter covers normalization, star and snowflake schemas, and slowly changing dimensions.

Star vs snowflake schema

Normalization

  • 1NF: atomic values, no repeating groups.
  • 2NF: no partial dependency on composite keys.
  • 3NF: no transitive dependencies.
  • Good for OLTP; reduces redundancy and update anomalies.

Slowly changing dimensions

  • SCD Type 1: overwrite old value, no history.
  • SCD Type 2: keep history with start/end dates and active flag.
  • SCD Type 3: keep previous value in a separate column.
-- SCD Type 2 customer dimension example
CREATE TABLE dim_customer (
    customer_key SERIAL PRIMARY KEY,
    customer_id VARCHAR(50) NOT NULL,
    full_name VARCHAR(200) NOT NULL,
    email VARCHAR(255) NOT NULL,
    valid_from DATE NOT NULL,
    valid_to DATE,
    is_current BOOLEAN NOT NULL DEFAULT TRUE
);

-- Query current view of customers
SELECT customer_id, full_name, email
FROM dim_customer
WHERE is_current = TRUE;

Chapter 5

OLTP vs OLAP

Online Transaction Processing (OLTP) and Online Analytical Processing (OLAP) serve very different purposes. Many data pipelines extract from OLTP systems and load into OLAP systems for reporting.

Dimension OLTP OLAP
Goal Record business transactions Analyze trends and patterns
Writes Many small, fast inserts/updates Mostly bulk loads, few updates
Reads Look up single rows Scan and aggregate huge ranges
Schema Normalized, many tables Star/snowflake, wide tables
Examples PostgreSQL, MySQL Snowflake, BigQuery, Redshift

Typical flow

Application writes to OLTP → pipeline extracts → transforms → loads into OLAP warehouse → analysts and dashboards consume.

Chapter 6

Data Engineering Lifecycle

The lifecycle is a simple mental model for every data project: generation, ingestion, storage, transformation, and serving. Governance, security, and quality cross all stages.

Lifecycle stages

Horizontal concerns

  • Data quality: profiling, validation, testing.
  • Governance: lineage, metadata, access control.
  • Security: encryption, masking, authentication.

Common outputs

  • Data warehouses, lakes, and lakehouses.
  • BI dashboards and self-service analytics.
  • Machine learning feature stores.

Chapter 8

Capstone: Healthcare FHIR Data Foundation

1. What is this project?

You will build a small healthcare data foundation using FHIR (Fast Healthcare Interoperability Resources) patient and observation data. The goal is to load sample JSON, normalize it into relational tables, and model a star schema for reporting.

2. What it covers?

  • Understanding FHIR Patient and Observation resources.
  • Normalizing nested JSON into relational tables.
  • Building a star schema for analytics.
  • Writing SQL cohort queries.
  • Documenting data lineage and collection considerations.

3. How it is done?

Load the sample JSON, design normalized tables, build dimensions and a fact table, then run cohort queries. The examples use SQLite-compatible SQL for portability.

{
  "resourceType": "Patient",
  "id": "P001",
  "name": [{ "family": "Doe", "given": ["Jane"] }],
  "gender": "female",
  "birthDate": "1985-03-10"
}
-- Normalized relational model (SQLite/Postgres compatible)
CREATE TABLE patient (
    patient_id TEXT PRIMARY KEY,
    family_name TEXT NOT NULL,
    given_name TEXT NOT NULL,
    gender TEXT,
    birth_date DATE
);

CREATE TABLE observation (
    observation_id TEXT PRIMARY KEY,
    patient_id TEXT REFERENCES patient(patient_id),
    code TEXT NOT NULL,
    display TEXT,
    value_numeric REAL,
    unit TEXT,
    effective_date DATE
);

CREATE TABLE dim_patient (
    patient_key INTEGER PRIMARY KEY,
    patient_id TEXT,
    full_name TEXT,
    gender TEXT,
    age_group TEXT,
    valid_from DATE,
    valid_to DATE,
    is_current BOOLEAN
);

CREATE TABLE fact_observation (
    patient_key INTEGER REFERENCES dim_patient(patient_key),
    observation_date_key INTEGER,
    code TEXT,
    display TEXT,
    value_numeric REAL,
    unit TEXT
);
-- Patient cohort: adult females with blood pressure observations
SELECT p.patient_id, p.full_name, o.display, o.value_numeric, o.unit
FROM dim_patient p
JOIN fact_observation o ON o.patient_key = p.patient_key
WHERE p.gender = 'female'
  AND CAST((julianday('now') - julianday(p.birth_date)) / 365 AS INT) >= 18
  AND o.code = '8867-4'
  AND p.is_current = TRUE;

4. What did we learn from this capstone project?

  • Nested healthcare JSON maps cleanly to normalized relational tables.
  • A star schema separates dimensional context from measurable facts.
  • SCD Type 2 dimensions let you track patient changes over time.
  • Documenting lineage and source constraints is part of the model, not an afterthought.

5. How can I enhance this project in the future?

  • Load real FHIR bundles from the CMS or Synthea synthetic dataset.
  • Add SCD Type 2 tracking for patient address or provider changes.
  • Build a Python loader that parses JSON and inserts rows transactionally.
  • Connect the model to a dashboard or BI tool in the DataOps tutorial.
  • Add data quality checks for missing codes, units, and out-of-range values.
