Chapter 2

Data Ingestion Patterns

Ingestion is how data enters your platform. It can be batch or streaming, synchronous or asynchronous, push or pull. The right pattern depends on latency, volume, source capabilities, and cost.

Batch vs streaming

  • Batch: process bounded datasets on a schedule. Higher latency, lower cost.
  • Streaming: process records as they arrive. Lower latency, more operational complexity.

Sync vs async

  • Synchronous: caller waits for completion (REST API, query).
  • Asynchronous: source emits events, pipeline consumes later (queues, streams).

Chapter 3

ETL vs ELT vs Reverse ETL

ETL transforms data before loading. ELT loads raw data first and transforms inside the warehouse. Reverse ETL moves warehouse data back into operational systems.

ETL

Transform before load. Used when raw data must be cleaned, masked, or aggregated before storage.

ELT

Load raw, transform with SQL/dbt in the warehouse. Faster to build, easier to audit, scales with warehouse power.

Reverse ETL

Sync warehouse insights to SaaS tools (CRM, ads, support) so operations can act on them.

Chapter 4

Building Pipelines with Python

Python is the lingua franca of data engineering. Libraries like pandas, psycopg2, and requests let you extract, transform, and load data with a few lines of code.

# Save as load_json_to_staging.py, then run with uv
cat << 'EOF' > load_json_to_staging.py
# Minimal ELT: load raw JSON events into a Postgres staging table
import json
import psycopg2

conn = psycopg2.connect(
    host="localhost", dbname="events_db",
    user="de_user", password="de_pass"
)

def load_json_to_staging(path, conn):
    with open(path) as f, conn.cursor() as cur:
        cur.execute("""
            CREATE TABLE IF NOT EXISTS staging_events (
                event_id TEXT PRIMARY KEY,
                payload JSONB NOT NULL,
                loaded_at TIMESTAMPTZ DEFAULT now()
            );
        """)
        for line in f:
            record = json.loads(line)
            cur.execute(
                "INSERT INTO staging_events (event_id, payload) VALUES (%s, %s)",
                (record["event_id"], json.dumps(record))
            )
        conn.commit()

load_json_to_staging("events.jsonl", conn)
conn.close()
EOF

uv run --with psycopg2 load_json_to_staging.py

Extract best practices

  • Use incremental extracts when possible (last modified timestamp).
  • Capture raw payloads before transformation for auditability.
  • Handle API rate limits with retries and backoff.

Chapter 5

Apache Airflow

Apache Airflow is an open-source orchestrator. You define workflows as DAGs (directed acyclic graphs) of tasks written in Python. Airflow handles scheduling, retries, dependencies, and observability.

# Minimal Airflow DAG (requires airflow installed)
from datetime import datetime, timedelta
from airflow import DAG
from airflow.operators.python import PythonOperator

def extract(): print("Extracting events...")
def load(): print("Loading raw events...")
def transform(): print("Running dbt...")

with DAG(
    "saas_elt",
    start_date=datetime(2024, 9, 1),
    schedule_interval="@daily",
    catchup=False,
    default_args={"retries": 2, "retry_delay": timedelta(minutes=5)},
) as dag:
    t1 = PythonOperator(task_id="extract", python_callable=extract)
    t2 = PythonOperator(task_id="load", python_callable=load)
    t3 = PythonOperator(task_id="transform", python_callable=transform)

    t1 >> t2 >> t3

Running with uv

A DAG file is normally parsed by Airflow rather than executed directly. Install Airflow as a persistent tool with uv tool install apache-airflow, or run a syntax check with uv run --with apache-airflow dag.py.

Airflow concepts

  • DAG: a workflow definition.
  • Task: a single unit of work in a DAG.
  • Operator: a template for a task (Python, SQL, Bash, etc.).
  • Scheduler: decides when to run DAGs.

Alternatives

  • Luigi: Spotify's Python task pipeline.
  • Prefect: modern, code-first orchestrator.
  • Dagster: asset-oriented data orchestration.

Chapter 6

dbt for Transformations

dbt (data build tool) lets you write data transformations as SQL select statements. It adds version control, documentation, tests, and a dependency graph on top of your warehouse.

-- models/staging/stg_events.sql
SELECT
  payload->>'event_id' AS event_id,
  (payload->>'user_id')::INT AS user_id,
  payload->>'event_type' AS event_type,
  payload->>'page' AS page,
  (payload->>'ts')::TIMESTAMPTZ AS event_ts
FROM staging_events

-- models/marts/fct_page_views.sql
SELECT
  event_id,
  user_id,
  page,
  event_ts,
  DATE_TRUNC('day', event_ts) AS event_date
FROM {{ ref('stg_events') }}
WHERE event_type = 'page_view'
# models/schema.yml: add tests to dbt models
version: 2
models:
  - name: stg_events
    columns:
      - name: event_id
        tests:
          - unique
          - not_null
      - name: user_id
        tests:
          - not_null

Chapter 7

Data Quality & Idempotency

Reliable pipelines are idempotent: running them twice produces the same result. Data quality checks catch issues before downstream consumers trust the data.

Idempotency techniques

  • Use INSERT ... ON CONFLICT or MERGE.
  • Partition tables by load date and overwrite partitions.
  • Track watermark/offset and resume from the last successful point.

Quality checks

  • Schema validation: expected columns and types.
  • Range checks: no negative prices, valid timestamps.
  • Uniqueness and referential integrity.
  • Freshness: data arrived within the expected window.
# Save as upsert_events.py, then run with uv
cat << 'EOF' > upsert_events.py
# Idempotent load: upsert events by event_id
import psycopg2
import json

conn = psycopg2.connect(
    host="localhost", dbname="events_db",
    user="de_user", password="de_pass"
)

def upsert_event(cur, event_id, payload):
    cur.execute("""
        INSERT INTO staging_events (event_id, payload)
        VALUES (%s, %s)
        ON CONFLICT (event_id) DO UPDATE SET payload = EXCLUDED.payload;
    """, (event_id, json.dumps(payload)))

with conn.cursor() as cur:
    upsert_event(cur, "evt_42", {"page": "/pricing"})
    conn.commit()

conn.close()
# This makes the pipeline safe to rerun for the same input file.
EOF

uv run --with psycopg2 upsert_events.py

Chapter 8

Capstone: SaaS ELT Pipeline

1. What is this project?

You will build an end-to-end ELT pipeline for a SaaS events dataset. The pipeline extracts events from CSV/JSON, loads them into Postgres, cleans them with dbt, and runs daily under Airflow.

2. What it covers?

  • Extract events from CSV/JSON sources with Python.
  • Load raw data into Postgres staging tables.
  • Write dbt models for cleaned facts and dimensions.
  • Add an Airflow DAG for daily orchestration.
  • Add data quality checks and idempotency.

3. How it is done?

Use Python to read source files, Postgres as the warehouse, dbt for transformations, and Airflow to schedule. The examples are simplified to run locally.

# extract.py: read CSV and JSONL into a list of dicts
cat << 'EOF' > extract.py
import csv, json

def extract_csv(path):
    with open(path, newline="") as f:
        return list(csv.DictReader(f))

def extract_jsonl(path):
    rows = []
    with open(path) as f:
        for line in f:
            rows.append(json.loads(line))
    return rows

raw_events = extract_csv("events.csv") + extract_jsonl("events.jsonl")
print(f"Loaded {len(raw_events)} raw events")
EOF

uv run extract.py
# load.py: idempotent load into Postgres staging
cat << 'EOF' > load.py
import psycopg2, json, csv

def extract_csv(path):
    with open(path, newline="") as f:
        return list(csv.DictReader(f))

def extract_jsonl(path):
    rows = []
    with open(path) as f:
        for line in f:
            rows.append(json.loads(line))
    return rows

raw_events = extract_csv("events.csv") + extract_jsonl("events.jsonl")

conn = psycopg2.connect(host="localhost", dbname="events_db",
                        user="de_user", password="de_pass")
cur = conn.cursor()
cur.execute("""
CREATE TABLE IF NOT EXISTS staging_events (
    event_id TEXT PRIMARY KEY,
    user_id INT,
    event_type TEXT,
    page TEXT,
    event_ts TIMESTAMPTZ,
    loaded_at TIMESTAMPTZ DEFAULT now()
);
""")

for row in raw_events:
    cur.execute("""
        INSERT INTO staging_events (event_id, user_id, event_type, page, event_ts)
        VALUES (%s, %s, %s, %s, %s)
        ON CONFLICT (event_id) DO UPDATE SET
            user_id = EXCLUDED.user_id,
            event_type = EXCLUDED.event_type,
            page = EXCLUDED.page,
            event_ts = EXCLUDED.event_ts;
    """, (row["event_id"], row["user_id"], row["event_type"],
          row.get("page"), row.get("event_ts")))

conn.commit()
conn.close()
EOF

uv run --with psycopg2 load.py
-- models/staging/stg_events.sql
SELECT
    event_id,
    user_id,
    LOWER(TRIM(event_type)) AS event_type,
    page,
    event_ts
FROM staging_events
WHERE user_id IS NOT NULL
  AND event_ts IS NOT NULL

# dag.py: Airflow orchestration
from datetime import datetime, timedelta
from airflow import DAG
from airflow.operators.bash import BashOperator

with DAG(
    "saas_elt",
    start_date=datetime(2024, 9, 1),
    schedule_interval="@daily",
    catchup=False,
    default_args={"retries": 1, "retry_delay": timedelta(minutes=5)},
) as dag:
    extract_load = BashOperator(
        task_id="extract_load",
        bash_command="uv run --with psycopg2 /opt/pipeline/load.py"
    )
    dbt_run = BashOperator(
        task_id="dbt_run",
        bash_command="uv run --with dbt-core,dbt-postgres dbt run --select marts"
    )
    dbt_test = BashOperator(
        task_id="dbt_test",
        bash_command="uv run --with dbt-core,dbt-postgres dbt test"
    )

    extract_load >> dbt_run >> dbt_test

Running with uv

Install Airflow as a persistent tool with uv tool install apache-airflow, or validate the DAG file with uv run --with apache-airflow dag.py. The BashOperator commands above use uv run --with so dependencies are resolved inline.

4. What did we learn from this capstone project?

  • ELT keeps raw data accessible while letting SQL transformations be versioned and tested.
  • Idempotent loads prevent duplicates when a pipeline reruns.
  • dbt tests turn assumptions into CI-checkable rules.
  • Airflow turns a set of scripts into a scheduled, observable workflow.

5. How can I enhance this project in the future?

  • Add partitioning by event_date to the fact table.
  • Move sources to S3 and trigger extraction on file arrival.
  • Add Great Expectations or Soda for richer data quality checks.
  • Containerize the pipeline with Docker and run in Kubernetes.
  • Emit lineage metadata to a catalog like DataHub or OpenLineage.
