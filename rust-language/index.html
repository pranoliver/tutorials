Rust: Systems Programming with Safety & Concurrency

Chapter 1

Introduction + Installation

Rust is a systems programming language that guarantees memory safety and thread safety without a garbage collector. It compiles to native code, runs everywhere C does, and is used for operating systems, browsers, game engines, blockchains, and cloud infrastructure.

Why learn Rust?

  • Memory safety: The borrow checker prevents null pointers, use-after-free, and data races at compile time.
  • Performance: Zero-cost abstractions with predictable memory layout and no runtime garbage collector.
  • Concurrency: Fearless parallelism thanks to ownership and type system guarantees.
  • Tooling: Cargo, rustfmt, clippy, and rust-analyzer give a polished developer experience.
  • Ecosystem: Crates.io hosts high-quality libraries for web services, embedded, cryptography, and more.

Before you start

  • A text editor and a terminal. New to the command line? Try the Linux tutorial.
  • Optional: Git basics for saving your projects.
  • No systems-programming background required, but patience with compiler errors helps.

Chapter 3

Ownership

Ownership is Rust's core memory-management rule. Every value has a single owner, and when the owner goes out of scope the value is dropped. This removes the need for a garbage collector while preventing use-after-free and double-free bugs. 

fn main() {
    let s1 = String::from("hello"); // s1 owns the String
    let s2 = s1;                    // ownership moves to s2
    // println!("{}", s1);          // ERROR: value borrowed after move
    println!("{}", s2);             // OK
} // s2 dropped here, heap memory freed

Ownership rules

  • Each value has exactly one owner.
  • When the owner leaves scope, the value is dropped.
  • Ownership can be moved, borrowed, or copied (for Copy types).

Copy vs Clone

Scalars and small fixed-size types implement Copy, so assignment duplicates instead of moving. Heap-allocated types like String and Vec move by default and must be explicitly cloned.

fn take_ownership(s: String) {
    println!("took: {}", s);
} // s is dropped here

fn main() {
    let s = String::from("rust");
    take_ownership(s); // s moves into the function
    // println!("{}", s); // ERROR

    let x = 42;        // i32 is Copy
    copy_value(x);
    println!("still have {}", x); // OK
}

fn copy_value(n: i32) {
    println!("copied: {}", n);
}
fn gives_ownership() -> String {
    String::from("yours")
}

fn takes_and_gives_back(s: String) -> String {
    s // ownership returned to caller
}

fn main() {
    let s1 = gives_ownership();
    let s2 = takes_and_gives_back(s1);
    println!("{}", s2);
}

Chapter 4

Borrowing & References

Borrowing lets code use a value without taking ownership. References are immutable by default; mutable references let you modify borrowed data under strict aliasing rules. 

fn main() {
    let s = String::from("hello");
    let len = calculate_length(&s); // immutable borrow
    println!("'{}' length is {}", s, len); // s still valid
}

fn calculate_length(s: &String) -> usize {
    s.len()
}
fn main() {
    let mut s = String::from("hello");
    change(&mut s);
    println!("{}", s);
}

fn change(s: &mut String) {
    s.push_str(", world");
}

Borrowing rules

  • Any number of immutable references &T, OR one mutable reference &mut T.
  • References must always be valid (no dangling references).
  • Mutable references prevent data races while still allowing zero-cost access.
fn main() {
    let mut s = String::from("hello");

    let r1 = &s;
    let r2 = &s;       // OK: multiple immutable borrows
    println!("{} {}", r1, r2);

    let r3 = &mut s;  // OK: after immutable borrows end
    r3.push('!');
    println!("{}", r3);
}

Chapter 5

Lifetimes

Lifetimes are compile-time annotations that tell the compiler how long references live. In most code they are inferred; you write them explicitly when a function accepts or returns a reference and the compiler cannot determine the relationship. 

fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}

fn main() {
    let s1 = String::from("long");
    let s2 = "short";
    let result = longest(&s1, s2);
    println!("longest is {}", result);
}

Lifetime elision

The compiler applies three common rules automatically, so simple functions rarely need explicit lifetimes.

'static

A 'static reference lives for the entire program. String literals and global constants are 'static.

struct Book<'a> {
    title: &'a str,
}

impl<'a> Book<'a> {
    fn excerpt(&self, text: &'a str) -> &'a str {
        text
    }
}

fn main() {
    let title = String::from("The Rust Book");
    let book = Book { title: &title };
    println!("{}", book.title);
}

Chapter 6

Structs & Enums

Structs bundle related data. Enums define a type that can be one of several variants. Combined with pattern matching, they make state machines and domain modeling expressive and safe. 

struct User {
    username: String,
    email: String,
    active: bool,
}

fn main() {
    let mut user = User {
        username: String::from("ada"),
        email: String::from("ada@example.com"),
        active: true,
    };
    user.email = String::from("ada@new.com");
    println!("{} <{}>", user.username, user.email);
}
enum Message {
    Quit,
    Move { x: i32, y: i32 },
    Write(String),
    ChangeColor(u8, u8, u8),
}

impl Message {
    fn describe(&self) -> &'static str {
        match self {
            Message::Quit => "quit",
            Message::Move { .. } => "move",
            Message::Write(_) => "write",
            Message::ChangeColor(_, _, _) => "color",
        }
    }
}

Tuple structs

struct Point(f64, f64);
struct Meters(u32);

let p = Point(1.0, 2.0);
println!("x = {}", p.0);

Unit structs

A struct with no fields is a unit struct. It is useful for type-level markers and zero-sized types.

struct Empty;

Chapter 8

Error Handling

Rust has no exceptions. Recoverable errors use Result<T, E>. Optional values use Option<T>. Unrecoverable bugs use panic!. 

fn main() {
    let some_number = Some(5);
    let absent: Option<i32> = None;

    match some_number {
        Some(n) => println!("got {}", n),
        None => println!("nothing"),
    }

    if let Some(n) = absent {
        println!("{}", n);
    }
}
use std::fs::File;

fn open_file(path: &str) -> Result<File, std::io::Error> {
    let f = File::open(path)?; // propagate errors with ?
    Ok(f)
}

fn main() {
    match open_file("hello.txt") {
        Ok(file) => println!("opened {:?}", file),
        Err(e) => println!("error: {}", e),
    }
}

Combining Results

let text = std::fs::read_to_string("data.txt")
    .unwrap_or_else(|_| String::from("default"));

let n: i32 = "42".parse().expect("not a number");

Chapter 9

Generics

Generics let you write code that works across many concrete types. Rust monomorphizes generic code, generating specialized machine code at compile time with no runtime overhead. 

fn largest<T: std::cmp::PartialOrd>(list: &[T]) -> &T {
    let mut biggest = &list[0];
    for item in list {
        if item > biggest { biggest = item; }
    }
    biggest
}

fn main() {
    let nums = [1, 5, 3, 8, 2];
    println!("largest number is {}", largest(&nums));

    let words = ["cat", "elephant", "dog"];
    println!("largest word is {}", largest(&words));
}
struct Wrapper<T> {
    value: T,
}

impl<T> Wrapper<T> {
    fn new(value: T) -> Self {
        Wrapper { value }
    }
}

fn main() {
    let w = Wrapper::new(String::from("hello"));
    println!("{}", w.value);
}

Chapter 10

Traits

Traits define shared behavior, similar to interfaces in other languages. They enable polymorphism, operator overloading, and the rich standard-library abstractions you use every day. 

pub trait Summary {
    fn summarize(&self) -> String;

    fn default_summary(&self) -> String {
        String::from("(read more)")
    }
}

struct Article {
    headline: String,
}

impl Summary for Article {
    fn summarize(&self) -> String {
        format!("{}", self.headline)
    }
}

fn notify(item: &impl Summary) {
    println!("Breaking! {}", item.summarize());
}

Common standard traits

  • Clone, Copy — duplication semantics.
  • Debug, Display — formatting for {:?} and {}.
  • PartialOrd, Ord — comparison.
  • Default, Drop — construction and destruction.

Chapter 11

Closures & Iterators

Closures are anonymous functions that capture their environment. Iterators produce sequences of values lazily and compose into readable data-processing pipelines. 

fn main() {
    let threshold = 10;
    let is_big = |n: i32| n > threshold; // closure borrows threshold

    let nums = vec![3, 12, 7, 25, 5];
    let big: Vec<i32> = nums.into_iter().filter(&is_big).collect();
    println!("{:?}", big);
}
fn main() {
    let scores = vec![55, 82, 91, 67, 78];

    let sum: i32 = scores.iter().sum();
    let avg = sum as f64 / scores.len() as f64;

    let doubled: Vec<i32> = scores.iter().map(|x| x * 2).collect();
    let first_pass = scores.iter().find(|&&x| x >= 90);

    println!("sum = {}, avg = {:.1}", sum, avg);
    println!("doubled = {:?}", doubled);
    println!("first pass = {:?}", first_pass);
}

Iterator adapters

  • map, filter, fold, zip — transform and aggregate.
  • collect — materialize into a collection.
  • iter() borrows, iter_mut() mutably borrows, into_iter() consumes.

Chapter 12

Modules & Crates

Modules organize code into namespaces. Crates are compilation units: binaries have a main entry, libraries have a lib.rs. Use pub to expose items and use to bring names into scope. 

// src/lib.rs
pub mod network;

pub mod utils {
    pub fn greet(name: &str) -> String {
        format!("Hello, {}", name)
    }
}

pub struct Config {
    pub host: String,
    pub port: u16,
}
// src/network.rs
pub fn connect() {
    println!("connecting...");
}

// src/main.rs
use my_crate::network;
use my_crate::utils::greet;

fn main() {
    network::connect();
    println!("{}", greet("Rust"));
}

Visibility

  • pub — visible everywhere.
  • pub(crate) — visible within the crate.
  • pub(super) — visible to parent module.
  • Default is private to the module.

Workspaces

Cargo workspaces let multiple related crates share a single Cargo.lock and build directory. Large projects like tokio use workspaces.

Chapter 14

Concurrency

Rust's ownership and type system eliminate data races at compile time. Threads, message passing, shared-state primitives, and async runtimes all build on the same safety guarantees. 

use std::thread;

fn main() {
    let handle = thread::spawn(|| {
        for i in 1..=3 {
            println!("spawned: {}", i);
        }
    });

    for i in 1..=3 {
        println!("main: {}", i);
    }

    handle.join().unwrap();
}
use std::sync::mpsc;

fn main() {
    let (tx, rx) = mpsc::channel();

    thread::spawn(move || {
        tx.send(String::from("hi from worker")).unwrap();
    });

    let msg = rx.recv().unwrap();
    println!("got: {}", msg);
}
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let counter = Arc::new(Mutex::new(0));
    let mut handles = vec![];

    for _ in 0..10 {
        let c = Arc::clone(&counter);
        let h = thread::spawn(move || {
            let mut num = c.lock().unwrap();
            *num += 1;
        });
        handles.push(h);
    }

    for h in handles { h.join().unwrap(); }
    println!("result = {}", *counter.lock().unwrap());
}

Concurrency primitives

  • std::thread — native OS threads.
  • mpsc — multi-producer single-consumer channels.
  • Mutex — mutual exclusion around shared data.
  • Arc — atomically reference-counted shared ownership.
  • RwLock — many readers or one writer.

Chapter 15

Unsafe Rust & FFI

Unsafe Rust lets you dereference raw pointers, call functions in other languages, and implement low-level primitives. It does not turn off the borrow checker, but it allows five additional powers that you must verify manually.

Unsafe superpowers

  • Dereference raw pointers *const T / *mut T.
  • Call an unsafe function or trait.
  • Implement an unsafe trait.
  • Access or modify a mutable static variable.
  • Access fields of a union.
unsafe fn dangerous() {}

fn main() {
    unsafe {
        dangerous();
    }
}

// Safe wrapper around unsafe code
fn split_at_mut(values: &mut [i32], mid: usize) -> (&mut [i32], &mut [i32]) {
    let len = values.len();
    assert!(mid <= len);
    let ptr = values.as_mut_ptr();
    unsafe {
        (
            std::slice::from_raw_parts_mut(ptr, mid),
            std::slice::from_raw_parts_mut(ptr.add(mid), len - mid),
        )
    }
}
extern "C" {
    fn abs(input: i32) -> i32;
}

#[no_mangle]
pub extern "C" fn rust_greet() {
    println!("hello from Rust");
}

fn main() {
    unsafe {
        println!("C abs(-3) = {}", abs(-3));
    }
}

Chapter 16

Async / Await

Async Rust lets a single thread run many concurrent tasks. An async block returns a Future; .await yields control until the future is ready. You need a runtime such as tokio to drive futures to completion. 

// Cargo.toml dependency: tokio = { version = "1", features = ["full"] }

#[tokio::main]
async fn main() {
    let task = tokio::spawn(async {
        println!("running in background");
        42
    });

    let result = task.await.unwrap();
    println!("result = {}", result);
}
async fn fetch(url: &str) -> Result<String, reqwest::Error> {
    let body = reqwest::get(url).await?.text().await?;
    Ok(body)
}

#[tokio::main]
async fn main() {
    match fetch("https://example.com").await {
        Ok(body) => println!("{} bytes", body.len()),
        Err(e) => eprintln!("failed: {}", e),
    }
}

Async building blocks

  • Future — a value that may not be ready yet.
  • .await — pause until the future resolves.
  • tokio::spawn — run a future concurrently.
  • tokio::select! — wait for one of several futures.

Capstone Projects

These three projects bring together ownership, concurrency, async, and the crate ecosystem. Build one, then return for the others.

Project A: Tiny Async HTTP/JSON API Server

1. What is this project?

Build a small REST-like JSON API using Tokio and Axum. It serves a list of tasks, lets clients create new tasks, and returns JSON. The goal is to practice ownership across async boundaries and Cargo dependency management.

2. What it covers?

  • Async/await with Tokio.
  • Shared state protected by Arc<Mutex<T>>.
  • JSON serialization with serde.
  • HTTP routing with Axum handlers.

3. How it is done?

# Cargo.toml
[package]
name = "todo-api"
version = "0.1.0"
edition = "2021"

[dependencies]
tokio = { version = "1", features = ["full"] }
axum = "0.7"
serde = { version = "1.0", features = ["derive"] }
serde_json = "1.0"
use axum::{
    extract::State, response::Json, routing::{get, post}, Router,
};
use serde::{Deserialize, Serialize};
use std::sync::{Arc, Mutex};

#[derive(Clone, Serialize, Deserialize)]
struct Task { id: u64, title: String }

#[derive(Default, Clone)]
struct AppState {
    tasks: Arc<Mutex<Vec<Task>>>,
    next_id: Arc<Mutex<u64>>,
}

async fn list_tasks(State(state): State<AppState>) -> Json<Vec<Task>> {
    let tasks = state.tasks.lock().unwrap().clone();
    Json(tasks)
}

#[tokio::main]
async fn main() {
    let state = AppState::default();
    let app = Router::new()
        .route("/tasks", get(list_tasks).post(create_task))
        .with_state(state);

    let listener = tokio::net::TcpListener::bind("127.0.0.1:3000")
        .await.unwrap();
    axum::serve(listener, app).await.unwrap();
}

async fn create_task(
    State(state): State<AppState>,
    Json(body): Json<CreateTask>,
) -> Json<Task> {
    let id = {
        let mut next = state.next_id.lock().unwrap();
        *next += 1;
        *next
    };
    let task = Task { id, title: body.title };
    state.tasks.lock().unwrap().push(task.clone());
    Json(task)
}

#[derive(Deserialize)]
struct CreateTask { title: String }

4. What did we learn?

  • Shared mutable state in async Rust needs explicit synchronization.
  • Axum extracts state and request bodies through handler signatures.
  • Serde derives turn structs into JSON automatically.

5. How can I enhance?

  • Add DELETE /tasks/:id and PATCH /tasks/:id endpoints.
  • Persist tasks to a SQLite database with sqlx.
  • Add structured logging with tracing.

Project B: Concurrent Log Parser Pipeline

1. What is this project?

Read a log file, send lines through a channel to worker threads, count log levels, and produce a summary. This shows ownership, message passing, and thread synchronization without data races.

2. What it covers?

  • Producer/consumer pattern with channels.
  • Shared counters via Arc<Mutex<...>>.
  • Iterator pipelines for parsing lines.
  • Graceful worker shutdown.

3. How it is done?

use std::collections::HashMap;
use std::fs::File;
use std::io::{BufRead, BufReader};
use std::sync::{mpsc, Arc, Mutex};
use std::thread;

fn main() {
    let (tx, rx) = mpsc::channel();
    let rx = Arc::new(Mutex::new(rx));
    let counts = Arc::new(Mutex::new(HashMap::new()));

    let worker_count = 4;
    let mut handles = vec![];

    for _ in 0..worker_count {
        let rx = Arc::clone(&rx);
        let counts = Arc::clone(&counts);
        let h = thread::spawn(move || {
            loop {
                let line = {
                    let lock = rx.lock().unwrap();
                    lock.recv()
                };
                match line {
                    Ok(l) => {
                        let level = l.split_whitespace()
                            .nth(2).unwrap_or("UNKNOWN");
                        let mut c = counts.lock().unwrap();
                        *c.entry(level.to_string()).or_insert(0) += 1;
                    }
                    Err(_) => break,
                }
            }
        });
        handles.push(h);
    }

    let file = File::open("app.log").expect("open log");
    for line in BufReader::new(file).lines() {
        tx.send(line.unwrap()).unwrap();
    }
    drop(tx); // signal workers to stop

    for h in handles { h.join().unwrap(); }
    println!("{:?}", counts.lock().unwrap());
}

4. What did we learn?

  • Channels decouple producers and consumers.
  • Dropping the transmitter closes the channel safely.
  • Mutexes should be held for the shortest time possible.

5. How can I enhance?

  • Write results to a JSON or CSV file.
  • Parse timestamps and compute error rates per minute.
  • Use crossbeam channels for higher throughput.

Project C: CLI Config Tool with clap and serde

1. What is this project?

Build a command-line tool that reads and writes a TOML configuration file. Users can get, set, and list keys. The project exercises traits, error handling, and third-party crate integration.

2. What it covers?

  • CLI parsing with derive macros (clap).
  • Structured config serialization with serde and toml.
  • Custom error types and the ? operator.
  • File I/O with std::fs.

3. How it is done?

# Cargo.toml
[package]
name = "cfg-cli"
version = "0.1.0"
edition = "2021"

[dependencies]
clap = { version = "4", features = ["derive"] }
serde = { version = "1.0", features = ["derive"] }
toml = "0.8"
use clap::{Parser, Subcommand};
use serde::{Deserialize, Serialize};
use std::collections::HashMap;
use std::fs;

#[derive(Serialize, Deserialize, Default)]
struct Config {
    values: HashMap<String, String>,
}

#[derive(Parser)]
#[command(name = "cfg-cli")]
struct Cli {
    #[command(subcommand)]
    cmd: Commands,
}

#[derive(Subcommand)]
enum Commands {
    Get { key: String },
    Set { key: String, value: String },
    List,
}

fn load(path: &str) -> Result<Config, Box<dyn std::error::Error>> {
    if !std::path::Path::new(path).exists() {
        return Ok(Config::default());
    }
    let text = fs::read_to_string(path)?;
    Ok(toml::from_str(&text)?)
}

fn save(path: &str, cfg: &Config) -> Result<(), Box<dyn std::error::Error>> {
    fs::write(path, toml::to_string_pretty(cfg)?)?;
    Ok(())
}

fn main() -> Result<(), Box<dyn std::error::Error>> {
    let path = "config.toml";
    let mut cfg = load(path)?;

    match Cli::parse().cmd {
        Commands::Get { key } => {
            match cfg.values.get(&key) {
                Some(v) => println!("{} = {}", key, v),
                None => println!("key not found"),
            }
        }
        Commands::Set { key, value } => {
            cfg.values.insert(key, value);
            save(path, &cfg)?;
        }
        Commands::List => {
            for (k, v) in &cfg.values {
                println!("{} = {}", k, v);
            }
        }
    }
    Ok(())
}

4. What did we learn?

  • Derive macros reduce boilerplate for CLI flags and config structs.
  • Box<dyn Error> is a quick way to propagate mixed error types.
  • Reading and writing files stays safe through ownership and ?.

5. How can I enhance?

  • Support nested keys with dot syntax, e.g. db.host.
  • Add an unset command and default values.
  • Replace Box<dyn Error> with thiserror for typed errors.
