Chapter 2

Data Serving & BI

Data serving is the last stage of the data lifecycle. The goal is to put trustworthy data in front of decision makers through dashboards, reports, APIs, and self-service analytics.

BI tools

  • Tableau, Power BI, Looker: enterprise BI.
  • Streamlit: Python-native data apps.
  • Superset, Metabase: open-source BI.

Data products

  • Dashboards and KPIs.
  • Feature stores for ML. See Machine Learning with Python.
  • Reverse ETL syncs to operational tools.
# dau_dashboard.py: Streamlit app to show daily active users
cat << 'EOF' > dau_dashboard.py
import streamlit as st
import pandas as pd

st.title("SaaS Daily Active Users")
df = pd.read_sql("""
    SELECT event_date, COUNT(DISTINCT user_key) AS dau
    FROM fact_events

Chapter 3

Reverse ETL

Reverse ETL moves curated data from the warehouse into operational systems. It closes the loop so that analytics directly powers actions in CRM, support, advertising, and product tools.

Common reverse ETL use cases

  • Sync customer lifetime value scores to Salesforce.
  • Send churn-risk segments to an email marketing platform.
  • Update ad audiences in Facebook/Google Ads.
  • Route high-priority support tickets based on customer tier.
-- Segment/audience to sync to CRM
SELECT
    user_id,
    segment_name,
    last_activity_date,
    predicted_churn_risk
FROM mlt_user_segments
WHERE segment_name = 'high_value_at_risk';
-- In practice, a reverse ETL tool (Census, Hightouch)
-- syncs this result to the CRM on a schedule.

Chapter 5

Monitoring Data Pipelines

You cannot trust data you cannot observe. Monitoring covers freshness, volume, schema changes, failures, and latency. Alerts should fire before stakeholders notice a problem.

Key metrics

  • Freshness: last successful run time.
  • Volume: rows processed vs expected.
  • Latency: end-to-end pipeline duration.
  • Error rate: failed tasks per DAG.

Tools

  • Airflow UI and statsd/Prometheus metrics.
  • dbt Cloud / dbt artifacts for test results.
  • Data observability: Monte Carlo, Bigeye, Soda.
# check_freshness.py: alert if no new events in 2 hours
cat << 'EOF' > check_freshness.py
import datetime
import psycopg2

def check_freshness(conn, threshold_hours=2):
    cur = conn.cursor()
    cur.execute("SELECT MAX(event_ts) FROM fact_events")
    last_ts = cur.fetchone()[0]
    if last_ts is None:
        return False
    age = datetime.datetime.utcnow() - last_ts
    return age < datetime.timedelta(hours=threshold_hours)

conn = psycopg2.connect(host="localhost", dbname="events_db",
                        user="de_user", password="de_pass")
print("Fresh:", check_freshness(conn))
conn.close()
EOF

uv run --with psycopg2 check_freshness.py

Chapter 6

Lineage & Metadata

Data lineage tracks where data came from, how it was transformed, and where it is used. Metadata management catalogs tables, schemas, owners, and quality signals so teams can discover and trust data.

Why lineage matters

  • Impact analysis before schema changes.
  • Root-cause analysis when a dashboard breaks.
  • Compliance: prove where PII flows.

Metadata tools

  • DataHub, OpenMetadata, Amundsen: open-source catalogs.
  • dbt docs: lineage from model dependencies.
  • OpenLineage: open standard for lineage events.
# Minimal lineage record stored in a metadata table
lineage_record = {
    "run_id": "run_20240912_001",
    "source": "staging_events",
    "target": "fct_events",
    "transformation": "dbt model: fct_events",
    "run_by": "airflow",
    "started_at": "2024-09-12T02:00:00Z",
    "status": "success"
}
# In production, emit this to OpenLineage or a metadata catalog.

Running with uv

To emit the lineage record to a catalog API, save it as record_lineage.py and run with the requests package:

uv run --with requests record_lineage.py

Chapter 7

Quality, Security, Privacy

Governance is the set of policies, controls, and practices that keep data accurate, secure, and compliant. It covers data quality, masking, encryption, access control, and regulations like GDPR and the EU AI Act.

Security controls

  • Encryption: at rest and in transit.
  • Authentication vs authorization: who you are vs what you can do.
  • Masking/obfuscation: hide PII for non-production use.

Regulations

  • GDPR: EU data protection, right to erasure, consent.
  • EU AI Act: risk-based rules for AI systems.
  • HIPAA: US healthcare data privacy and security.
# mask_pii.py: mask PII before loading to a lower environment
cat << 'EOF' > mask_pii.py
import hashlib

def mask_email(email):
    local, domain = email.split("@")
    return f"{local[:2]}***@{domain}"

def tokenize(value):
    return hashlib.sha256(value.encode()).hexdigest()[:16]

# Example usage
print(mask_email("jane.doe@hospital.org"))
print(tokenize("patient_123"))
EOF

uv run mask_pii.py

Chapter 8

Capstone: Governed Healthcare FHIR Data Platform

1. What is this project?

You will Dockerize the FHIR ETL pipeline from the foundations tutorial, add lineage tracking, implement PII masking and encryption for PHI, add data quality checks and monitoring alerts, and build a simple Streamlit governance dashboard.

2. What it covers?

  • Dockerize the FHIR ETL pipeline.
  • Add data lineage tracking and a metadata catalog.
  • Implement PII masking and encryption for PHI.
  • Add data quality checks and monitoring alerts.
  • Build a Streamlit governance dashboard.

3. How it is done?

Package the pipeline in Docker, record lineage in a small SQLite catalog, mask emails, encrypt sensitive fields, run quality checks after load, and surface results in Streamlit.

# Dockerfile for the governed FHIR pipeline
FROM python:3.11-slim
COPY --from=ghcr.io/astral-sh/uv:0.4 /uv /bin/uv

WORKDIR /app
COPY pyproject.toml .
COPY . /app
RUN uv pip install --system .

CMD ["uv", "run", "python", "fhir_pipeline.py"]
# fhir_pipeline.py: mask + encrypt + quality + lineage
cat << 'EOF' > fhir_pipeline.py
import sqlite3, json, hashlib
from cryptography.fernet import Fernet

key = Fernet.generate_key()
cipher = Fernet(key)

def mask_email(email):
    local, domain = email.split("@")
    return f"{local[:2]}***@{domain}"

def encrypt(text):
    return cipher.encrypt(text.encode()).decode()

def decrypt(token):
    return cipher.decrypt(token.encode()).decode()

def record_lineage(conn, source, target, status):
    conn.execute("""
        CREATE TABLE IF NOT EXISTS lineage (
            run_id INTEGER PRIMARY KEY,
            source TEXT,
            target TEXT,
            status TEXT,
            run_at TEXT DEFAULT CURRENT_TIMESTAMP
        )
    """)
    conn.execute(
        "INSERT INTO lineage (source, target, status) VALUES (?, ?, ?)",
        (source, target, status)
    )
    conn.commit()

def quality_check(conn):
    cur = conn.execute("""
        SELECT COUNT(*) FROM dim_patient
        WHERE full_name IS NULL OR email IS NULL
    """)
    bad = cur.fetchone()[0]
    return bad == 0

# Example transform
patient = {"patient_id": "P001", "full_name": "Jane Doe",
           "email": "jane.doe@hospital.org"}
patient["email_masked"] = mask_email(patient["email"])
patient["email_encrypted"] = encrypt(patient["email"])
print(patient)
EOF

uv run --with cryptography fhir_pipeline.py
# dashboard.py: Streamlit governance dashboard
cat << 'EOF' > dashboard.py
import streamlit as st
import sqlite3

st.title("FHIR Data Governance Dashboard")
conn = sqlite3.connect("fhir_catalog.db")

st.subheader("Lineage")
lineage = conn.execute("SELECT * FROM lineage ORDER BY run_at DESC LIMIT 10").fetchall()
st.dataframe(lineage)

st.subheader("Data Quality")
ok = conn.execute("""
    SELECT COUNT(*) = 0 FROM dim_patient
    WHERE full_name IS NULL OR email IS NULL
""").fetchone()[0]
st.metric("Quality Check", "Pass" if ok else "Fail")

st.subheader("PII Masking Sample")
st.write("jane.doe@hospital.org → j.***@hospital.org")
EOF

uv run --with streamlit dashboard.py
# Or launch the Streamlit server directly:
uv run --with streamlit streamlit run dashboard.py

4. What did we learn from this capstone project?

  • Docker makes the pipeline reproducible across environments.
  • Lineage records support audits and root-cause analysis.
  • Masking and encryption reduce PHI exposure risk.
  • Quality checks and a governance dashboard build trust with users and regulators.

  • Add role-based access control and audit logging.
  • Integrate Soda or Great Expectations for data contracts.
  • Add Prometheus/Grafana metrics and PagerDuty alerts.
  • Extend the dashboard with GDPR deletion request tracking.
