Chapter 1

Introduction to DSA

Imagine you have to find your friend's phone number in a contact list of 1,000 people. You could look at every name one by one — that works, but it's slow. Or, if the list is sorted alphabetically, you could open to the middle, see whether your friend's name comes before or after, and throw away half the list instantly. Repeat that a few times, and you find the name in about 10 steps instead of 1,000.

Data Structures & Algorithms (DSA) is exactly this idea, applied to computers. A data structure is a way to organize information so the computer can work with it efficiently — like a sorted contact list, a stack of plates, or a map of cities and roads. An algorithm is a clear, step-by-step recipe for solving a problem — like the "split the list in half" trick above.

Computers are fast, but they are not magic. If you give a computer a bad plan, even the fastest machine will crawl. Give it a good plan (a good algorithm) stored in a good layout (a good data structure), and the same problem that took hours can be solved in milliseconds. That's what DSA is all about: choosing the right way to organize data, and the right steps to process it.

Why DSA matters

  • Performance: Two programs can solve the same problem. One finishes in a second; the other takes minutes. The difference is almost always the algorithm and data structure they use.
  • Interviews: Tech companies use DSA questions to test how you think — not whether you memorized a language, but whether you can break a problem down and pick an efficient solution.
  • Foundation: Databases, compilers, operating systems, search engines, social networks, and AI all run on classic data structures (arrays, trees, graphs, hash tables) and algorithms (sorting, searching, pathfinding).
  • Everyday life: You already use DSA without knowing it — sorting your books, searching a playlist, following a recipe, or choosing the shortest route to school are all data structures and algorithms.

How to use this tutorial

Every code block is runnable Python. Copy it, paste it into a file (for example dsa_demo.py), and run it with python dsa_demo.py. Each example prints clear output so you can see exactly what happens. Don't just read the code — copy it, run it, change the numbers, and break it on purpose. That's how you learn.

Chapter 2

Complexity Analysis (Big O)

Imagine two students both have to sort 100 test papers alphabetically. One student reads every paper once and puts it in the right place. The other compares every paper against every other paper, again and again. Both finish with the same sorted stack, but the second student will still be working when the first student has gone home.

Big O notation is how computer scientists measure this difference. It tells us how much time or memory an algorithm needs as the input grows. We don't care about milliseconds on one specific laptop — we care about the shape of the work curve. Does the work stay flat? Does it double when the input doubles? Does it explode?

When we say an algorithm is O(n), we mean: if you give it twice as much data, it takes roughly twice as long. If it is O(n²), twice as much data means roughly four times as long. If it is O(1), it doesn't matter how big the data is — the time stays the same. Big O lets us compare two algorithms without running them on a real machine, and it helps us avoid writing code that looks fine with 10 items but dies with 10,000.

Common complexity classes

Here is a menu of the most common growth rates you will meet. The best ones are near the top; the scary ones are near the bottom. Notice that "log n" grows incredibly slowly — cutting a problem in half repeatedly is a superpower.

Big O Name What it means Real example
O(1)ConstantFlat line — work stays the same no matter how much dataReading the first item of a list
O(log n)LogarithmicVery slow growth — repeatedly cutting the problem in halfBinary search in a dictionary
O(n)LinearWork doubles when input doublesReading every page of a book
O(n log n)LinearithmicA little worse than linear; still very practicalEfficient sorting like merge sort
O(n²)QuadraticWork explodes when input grows — every item touches every itemChecking every pair in a class
O(2ⁿ)ExponentialTiny input becomes impossible quicklyTrying every combination of a password

Memory matters too. If an algorithm creates a brand-new copy of everything, it uses O(n) extra space. If it works "in place" using only a few variables, it uses O(1) extra space. Time and space are a trade-off: sometimes we use more memory to save time, and sometimes we keep memory tiny by doing a little more work.

Timing O(1) vs O(n) vs O(n²)

The following program creates lists of different sizes and measures three functions. Watch how the constant function barely changes, the linear function grows in step with the list, and the quadratic function quickly becomes painful.

"""Complexity demonstration: O(1), O(n), and O(n^2).
Run: python complexity_demo.py
"""

import time

def constant_time(arr):
    """O(1): Always one operation, regardless of array size."""
    return arr[0] if arr else None

def linear_time(arr, target):
    """O(n): Check each element once."""
    for item in arr:
        if item == target:
            return True
    return False

def quadratic_time(arr):
    """O(n^2): Nested loop over all pairs."""
    count = 0
    for i in arr:
        for j in arr:
            count += 1
    return count

def time_it(fn, *args):
    start = time.perf_counter()
    result = fn(*args)
    elapsed = (time.perf_counter() - start) * 1000  # milliseconds
    return result, elapsed

# Build arrays of different sizes
sizes = [1_000, 5_000, 10_000]
print(f"{'Size':>8} | {'O(1) ms':>9} | {'O(n) ms':>9} | {'O(n^2) ms':>11}")
print("-" * 46)

for n in sizes:
    arr = list(range(n))

    _, t1 = time_it(constant_time, arr)
    _, t2 = time_it(linear_time, arr, n - 1)  # worst case: last element
    _, t3 = time_it(quadratic_time, arr)

    print(f"{n:>8} | {t1:>9.4f} | {t2:>9.4f} | {t3:>11.4f}")

print("\nNotice: O(n^2) grows much faster than O(n) or O(1).")
# Sample output:
# Size    |   O(1) ms |   O(n) ms |  O(n^2) ms
# ----------------------------------------------
#    1000 |    0.0012 |    0.0234 |     3.4125
#    5000 |    0.0008 |    0.0412 |    85.2103
#   10000 |    0.0005 |    0.0987 |   342.1055

Chapter 3

Arrays & Lists

Think of an array like a row of numbered lockers in a school hallway. Each locker has a label: 0, 1, 2, 3, and so on. Because the lockers are in one straight line and each is the same size, you can walk directly to locker number 5 and open it immediately. You don't have to look inside lockers 0 through 4 first. That's why reading an item by its index is super fast — O(1).

A Python list is basically a flexible version of this locker row. You can add items to the end, insert in the middle, remove items, and read any position. The catch is that inserting or deleting in the middle is slow — every item after the changed spot has to slide over by one locker, like students in a bench scooting left or right to make room. That sliding takes O(n) time in the worst case.

Arrays are perfect when you mainly want to read items by position or add/remove from the end. They are the building blocks behind almost every other data structure. Even things like matrices, images, and sound clips are stored as arrays under the hood.

List operations demo

Run this program and watch the output. Notice how nums[2] gives the third item instantly, but nums.insert(1, 15) has to shift everything after it.

Two-sum problem (O(n) with a hash set)

Here is a classic array problem: you are given a list of numbers and a target. Find two numbers that add up to the target. The obvious way is to try every pair — that's O(n²). But we can do much better. As we walk through the list once, we remember each number we have seen in a hash table. For the current number, we ask: "have I already seen the number I need to reach the target?" That lookup is O(1), so the whole algorithm becomes O(n).

For example, if the target is 9 and the current number is 2, we ask: "have I seen 7 before?" If yes, we found our pair. If not, we store 2 and move on. One pass, one hash table, one answer. 

"""Two-sum: find two numbers that add to target. O(n) time, O(n) space.
Run: python two_sum.py
"""

def two_sum(nums, target):
    """Return indices of two numbers that sum to target, or None."""
    seen = {}  # value -> index
    for i, num in enumerate(nums):
        complement = target - num
        if complement in seen:          # O(1) lookup
            return [seen[complement], i]
        seen[num] = i                   # store for later lookups
    return None

# Demo
test_cases = [
    ([2, 7, 11, 15], 9),   # -> [0, 1] (2 + 7)
    ([3, 2, 4], 6),        # -> [1, 2] (2 + 4)
    ([3, 3], 6),           # -> [0, 1] (3 + 3)
    ([1, 2, 3], 7),        # -> None
]

for nums, target in test_cases:
    result = two_sum(nums, target)
    print(f"nums={nums}, target={target} -> indices={result}")
# Output:
# nums=[2, 7, 11, 15], target=9 -> indices=[0, 1]
# nums=[3, 2, 4], target=6 -> indices=[1, 2]
# nums=[3, 3], target=6 -> indices=[0, 1]
# nums=[1, 2, 3], target=7 -> indices=None

Chapter 4

Linked Lists

Imagine a treasure hunt where each clue points to the location of the next clue. You cannot jump to clue number 5; you must follow the chain from clue 1 to 2 to 3, reading each note as you go. A linked list works exactly like this treasure hunt. Each item, called a node, stores two things: its own data (the clue) and a pointer to the next node (where to look next).

Unlike an array, the nodes are not sitting next to each other in memory. They are scattered, connected only by these pointers. This makes inserting at the front fast — O(1) — because you just create a new node and make it point to the old head. Deleting the first item is also fast. But reading a specific index is slow — O(n) — because you have to walk the chain from the start.

Linked lists are great when you do lots of insertions and deletions at the ends, especially when you don't know the final size ahead of time. They are also the foundation of stacks, queues, and more advanced structures. The trade-off is simple: arrays give you fast random access; linked lists give you fast flexible insert/delete.

Singly linked list implementation

Below is a complete linked list from scratch in Python. Notice how the Node class only has two fields: data and next. The LinkedList class only needs to remember the head node. 

"""Singly linked list with append, prepend, delete, and print.
Run: python linked_list.py
"""

class Node:
    """A single node: holds data and a link to the next node."""
    def __init__(self, data):
        self.data = data
        self.next = None

class LinkedList:
    def __init__(self):
        self.head = None

    def prepend(self, data):
        """Insert at the front — O(1)."""
        new_node = Node(data)
        new_node.next = self.head
        self.head = new_node

    def append(self, data):
        """Insert at the end — O(n) because we walk to the tail."""
        new_node = Node(data)
        if not self.head:
            self.head = new_node
            return
        current = self.head
        while current.next:
            current = current.next
        current.next = new_node

    def delete(self, key):
        """Delete first node with matching data — O(n)."""
        current = self.head
        # Case: head holds the key
        if current and current.data == key:
            self.head = current.next
            current = None
            return
        # Search for the key, keeping track of previous node
        prev = None
        while current and current.data != key:
            prev = current
            current = current.next
        if not current:  # key not found
            return
        prev.next = current.next
        current = None

    def __str__(self):
        parts = []
        current = self.head
        while current:
            parts.append(str(current.data))
            current = current.next
        return " -> ".join(parts) if parts else "empty"

# Demo
ll = LinkedList()
ll.append(10)
ll.append(20)
ll.append(30)
print("After appends 10,20,30:", ll)        # 10 -> 20 -> 30

ll.prepend(5)
print("After prepend 5:    ", ll)           # 5 -> 10 -> 20 -> 30

ll.delete(20)
print("After delete 20:    ", ll)           # 5 -> 10 -> 30

ll.delete(99)  # not present
print("After delete 99:    ", ll)           # unchanged
# Output:
# After appends 10,20,30: 10 -> 20 -> 30
# After prepend 5:     5 -> 10 -> 20 -> 30
# After delete 20:     5 -> 10 -> 30
# After delete 99:     5 -> 10 -> 30

Chapter 5

Stacks & Queues

A stack is like a pile of plates. You add new plates on top, and when you need one, you also take from the top. The last plate you put down is the first one you pick up — that's why we call it LIFO: Last In, First Out. In a computer, the "undo" button in your text editor, the browser back button, and the way functions call each other all use stacks.

A queue is like a line at the cafeteria. The first person to arrive is the first person served. New people join at the back; service happens at the front. That's FIFO: First In, First Out. Your printer queue, a playlist, and the order in which web requests are handled all behave like queues.

Both structures only let you interact at specific ends. This seems like a limitation, but that limitation is exactly their power. Because they only care about one end (or two ends), every operation is O(1). They are the backbone of many algorithms, including the way we explore graphs and backtrack through choices.

Stack demo (list-based)

This demo shows a stack acting like an undo history. We push four actions, then pop twice to undo the two most recent ones. The last action pushed (italic) is the first one undone. 

"""Stack: Last-In First-Out (LIFO).
Run: python stack_demo.py
"""

class Stack:
    def __init__(self):
        self.items = []

    def push(self, item):
        self.items.append(item)          # O(1)

    def pop(self):
        if self.is_empty():
            raise IndexError("pop from empty stack")
        return self.items.pop()          # O(1)

    def peek(self):
        if self.is_empty():
            return None
        return self.items[-1]            # O(1)

    def is_empty(self):
        return len(self.items) == 0

    def __str__(self):
        return " -> ".join(str(x) for x in reversed(self.items)) or "empty"

# Undo-style demo
stack = Stack()
for action in ["type 'Hello'", "type ' World'", "bold", "italic"]:
    stack.push(action)
    print(f"Pushed: {action}")

print("\nStack top to bottom:", stack)
print("Undo (pop):", stack.pop())   # italic
print("Undo (pop):", stack.pop())   # bold
print("Stack now:", stack)
# Output:
# Pushed: type 'Hello'
# Pushed: type ' World'
# Pushed: bold
# Pushed: italic
#
# Stack top to bottom: italic -> bold -> type ' World' -> type 'Hello'
# Undo (pop): italic
# Undo (pop): bold
# Stack now: type ' World' -> type 'Hello'

Queue demo (collections.deque)

We use Python's collections.deque because popping from the front of a normal list is O(n) — every item has to shift. A deque is designed for fast O(1) push and pop at both ends, which makes it perfect for a queue. Watch how the first song queued is the first one played. 

"""Queue: First-In First-Out (FIFO) using deque for O(1) popleft.
Run: python queue_demo.py
"""

from collections import deque

class Queue:
    def __init__(self):
        self.items = deque()

    def enqueue(self, item):
        self.items.append(item)          # O(1)

    def dequeue(self):
        if self.is_empty():
            raise IndexError("dequeue from empty queue")
        return self.items.popleft()      # O(1)

    def peek(self):
        return self.items[0] if not self.is_empty() else None

    def is_empty(self):
        return len(self.items) == 0

    def __str__(self):
        return " <- ".join(str(x) for x in self.items) or "empty"

# Print-job demo
q = Queue()
for job in ["doc1.pdf", "doc2.pdf", "doc3.pdf"]:
    q.enqueue(job)
    print(f"Enqueued: {job}")

print("\nQueue front to back:", q)
print("Printing (dequeue):", q.dequeue())  # doc1.pdf
print("Printing (dequeue):", q.dequeue())  # doc2.pdf
print("Queue now:", q)
# Output:
# Enqueued: doc1.pdf
# Enqueued: doc2.pdf
# Enqueued: doc3.pdf
#
# Queue front to back: doc1.pdf <- doc2.pdf <- doc3.pdf
# Printing (dequeue): doc1.pdf
# Printing (dequeue): doc2.pdf
# Queue now: doc3.pdf

Chapter 6

Hash Tables

Imagine a giant set of pigeonholes in a school office. Each pigeonhole has a number. When a student hands in a form, the secretary uses the student's ID to decide which pigeonhole to put it in — for example, by adding up digits and taking the remainder. Later, to find the form, the secretary uses the same ID calculation and goes straight to that pigeonhole. No searching through every form. That's the magic of a hash table.

A hash table stores pairs of keys and values — like names and phone numbers, or words and definitions. A hash function converts the key into an index (a pigeonhole number). On average, inserting, looking up, and deleting are all O(1) — they take about the same time whether you have 10 entries or 10 million.

In Python, dict is a hash table. set is also a hash table, but it only stores keys (no values). The only gotcha is collisions: sometimes two different keys land in the same pigeonhole. Python handles this automatically using chaining (a mini linked list inside the pigeonhole). Good hash functions keep collisions rare.

Hash table demo (Python dict)

This is exactly how your phone's contact list or a dictionary app works. Keys are names, values are phone numbers. Lookups, inserts, and deletes are all fast because Python is using a hash table under the hood.

"""Count word frequencies using a hash map. O(n) time.

def word_frequencies(text):

Chapter 7

Trees & Binary Search Trees

A tree is like a family tree or an organization chart: one root node at the top, with branches that connect to child nodes, and those children may have their own children. Unlike a list, which has one "next," a tree node can have many children. This shape is perfect for representing hierarchies — folders on your computer, the HTML structure of a web page, or decisions in a game.

A binary search tree (BST) is a special tree where each node has at most two children, and the children follow a strict rule: every value in the left subtree is smaller, and every value in the right subtree is larger. This rule makes searching super fast. If you want to find a number, you compare it to the root; if it's smaller, you go left; if bigger, you go right. You discard half the tree at every step — just like the phone book trick.

In a balanced BST, each step cuts the data in half, so search, insert, and delete are O(log n). The catch is "if balanced." If you insert sorted data into a normal BST, it becomes a straight line — basically a linked list — and slows down to O(n). Real-world systems use self-balancing trees (like AVL or Red-Black trees) to prevent this.

Binary search tree implementation

The code below builds a BST from scratch. Each TreeNode has a key and two children (left and right). The insert and search methods follow the smaller-left, bigger-right rule recursively. 

"""Binary Search Tree (BST): insert, search, in-order traversal.
Run: python bst_demo.py
"""

class TreeNode:
    def __init__(self, key):
        self.key = key
        self.left = None
        self.right = None

class BST:
    def __init__(self):
        self.root = None

    def insert(self, key):
        """Insert a key — O(h) where h is tree height."""
        self.root = self._insert(self.root, key)

    def _insert(self, node, key):
        if node is None:
            return TreeNode(key)
        if key < node.key:
            node.left = self._insert(node.left, key)
        elif key > node.key:
            node.right = self._insert(node.right, key)
        return node

    def search(self, key):
        """Search for a key — O(h)."""
        return self._search(self.root, key)

    def _search(self, node, key):
        if node is None:
            return False
        if key == node.key:
            return True
        if key < node.key:
            return self._search(node.left, key)
        return self._search(node.right, key)

    def inorder(self):
        """Return keys in sorted order (left, root, right)."""
        result = []
        self._inorder(self.root, result)
        return result

    def _inorder(self, node, result):
        if node:
            self._inorder(node.left, result)
            result.append(node.key)
            self._inorder(node.right, result)

# Demo: insert in unsorted order, then traverse sorted
bst = BST()
for key in [50, 30, 70, 20, 40, 60, 80]:
    bst.insert(key)

print("In-order traversal (sorted):", bst.inorder())
# [20, 30, 40, 50, 60, 70, 80]

print("Search 40:", bst.search(40))  # True
print("Search 99:", bst.search(99))  # False
# Output:
# In-order traversal (sorted): [20, 30, 40, 50, 60, 70, 80]
# Search 40: True
# Search 99: False

Heaps & Priority Queues

A heap is a special tree that is always organized so that the most important item is at the top. In a min-heap, every parent node is smaller than or equal to its children — so the very smallest item is always at the root. In a max-heap, every parent is larger, so the biggest item is on top. Think of it like a hospital triage room: the most urgent patient is always seen next, even if new patients keep arriving.

Heaps are usually stored as arrays, but logically they behave like complete binary trees. The root is at index 0. The left child of index i is at index 2i + 1, and the right child is at 2i + 2. When you insert or remove, the heap "bubbles" items up or down to restore the parent-child ordering. Both insertion and removal take O(log n) time because the tree height is logarithmic.

A priority queue is the abstract idea: a queue where items have priorities and the highest-priority item is served first. A heap is the most common way to implement a priority queue. Python's heapq module gives you a min-heap for free. You will see heaps again in Dijkstra's algorithm and in the scheduler inside your operating system.

Min-heap demo (heapq)

This demo simulates a task scheduler. Each task has a priority number; the smallest number means "most urgent." Even though the tasks were inserted in random order, heappop always returns the most urgent remaining task first. 

"""Min-heap / priority queue with heapq.
Run: python heap_demo.py
"""

import heapq

class MinHeap:
    def __init__(self):
        self.heap = []

    def push(self, item):
        heapq.heappush(self.heap, item)   # O(log n)

    def pop(self):
        return heapq.heappop(self.heap)   # O(log n)

    def peek(self):
        return self.heap[0] if self.heap else None  # O(1)

    def __str__(self):
        return str(self.heap)

# Demo: task scheduler with priorities (lower number = higher priority)

Chapter 9

Graphs & Traversal

A graph is a collection of nodes (also called vertices) connected by edges. If this sounds familiar, it's because almost everything is a graph: cities connected by roads, people connected by friendships, web pages connected by links, or tasks connected by dependencies. Trees are actually a special kind of graph with no cycles.

When you want to explore a graph, there are two classic strategies. Breadth-First Search (BFS) explores evenly outward, like ripples in a pond. It visits all of the start node's neighbors first, then their neighbors, and so on. BFS is great for finding the shortest path in an unweighted graph because it reaches closer nodes before farther ones. It uses a queue.

Depth-First Search (DFS), on the other hand, dives deep. It picks one neighbor and follows that path as far as possible, then backtracks when it hits a dead end. DFS is useful for detecting cycles, exploring all possible paths, or ordering tasks that depend on other tasks. It uses a stack (often disguised as recursion). Both BFS and DFS visit every node once, giving them O(V + E) time where V is the number of vertices and E is the number of edges.

BFS & DFS on an adjacency list

The graph is stored as an adjacency list — a dictionary where each key is a node, and its value is a list of neighbors. This is the standard way to represent sparse graphs. Compare the BFS and DFS outputs; notice how BFS reaches C early while DFS saves it for last. 

"""Graph traversals: BFS and DFS.
Run: python graph_demo.py
"""

from collections import deque

# Graph as adjacency list
graph = {
    "A": ["B", "C"],
    "B": ["D", "E"],
    "C": ["F"],
    "D": [],
    "E": ["F"],
    "F": [],
}

def bfs(start):
    """Breadth-First Search using a queue."""
    visited = set()
    queue = deque([start])
    order = []
    while queue:
        node = queue.popleft()
        if node not in visited:
            visited.add(node)
            order.append(node)
            queue.extend(graph[node])
    return order

def dfs(start, visited=None, order=None):
    """Depth-First Search using recursion."""
    if visited is None:
        visited = set()
    if order is None:
        order = []
    visited.add(start)
    order.append(start)
    for neighbor in graph[start]:
        if neighbor not in visited:
            dfs(neighbor, visited, order)
    return order

print("BFS from A:", bfs("A"))    # A, B, C, D, E, F
print("DFS from A:", dfs("A"))    # A, B, D, E, F, C
# Output:
# BFS from A: ['A', 'B', 'C', 'D', 'E', 'F']
# DFS from A: ['A', 'B', 'D', 'E', 'F', 'C']

Chapter 10

Sorting Algorithms

Sorting is one of the most common things computers do. Before you can binary search a list, you need it sorted. Before you can find the top scores, you need them sorted. Before you can even compare two datasets, you often sort them first. A good sorting algorithm can save enormous amounts of time.

Here are four classic ways to sort. Bubble sort repeatedly walks through the list and swaps neighbors that are out of order, like bubbles rising to the surface. It is simple but slow — O(n²). Insertion sort builds the sorted part one item at a time, the way you might sort playing cards in your hand. It is also O(n²) in the worst case, but fast for small or nearly-sorted lists.

Merge sort uses the "divide and conquer" idea: split the list in half, sort each half, then merge the sorted halves together. Merging two sorted lists is easy — just repeatedly take the smaller front item. Merge sort is O(n log n) in all cases, which makes it very reliable. Quick sort also uses divide and conquer, but it picks a pivot and partitions items into "smaller than pivot" and "larger than pivot." On average it is O(n log n) and very fast in practice, but a bad pivot choice can make it O(n²).

Bubble sort, insertion sort, merge sort, quick sort

Run the code and compare the timings (if you increase input size). For tiny lists they all look similar; for large lists, bubble and insertion will become painfully slow while merge and quick stay efficient. 

"""Sorting algorithms demo.
Run: python sorting_demo.py
"""

def bubble_sort(arr):
    """O(n^2). Repeatedly swaps adjacent out-of-order elements."""
    a = arr[:]
    n = len(a)
    for i in range(n):
        for j in range(0, n - i - 1):
            if a[j] > a[j + 1]:
                a[j], a[j + 1] = a[j + 1], a[j]
    return a

def insertion_sort(arr):
    """O(n^2). Builds sorted array one element at a time."""
    a = arr[:]
    for i in range(1, len(a)):
        key = a[i]
        j = i - 1
        while j >= 0 and a[j] > key:
            a[j + 1] = a[j]
            j -= 1
        a[j + 1] = key
    return a

def merge_sort(arr):
    """O(n log n). Divide, recursively sort, merge."""
    if len(arr) <= 1:
        return arr
    mid = len(arr) // 2
    left = merge_sort(arr[:mid])
    right = merge_sort(arr[mid:])
    return _merge(left, right)

def _merge(left, right):
    result = []
    i = j = 0
    while i < len(left) and j < len(right):
        if left[i] <= right[j]:
            result.append(left[i]); i += 1
        else:
            result.append(right[j]); j += 1
    result.extend(left[i:])
    result.extend(right[j:])
    return result

def quick_sort(arr):
    """O(n log n) average, O(n^2) worst. Pivot-based partitioning."""
    if len(arr) <= 1:
        return arr
    pivot = arr[len(arr) // 2]
    left = [x for x in arr if x < pivot]
    middle = [x for x in arr if x == pivot]
    right = [x for x in arr if x > pivot]
    return quick_sort(left) + middle + quick_sort(right)

data = [64, 34, 25, 12, 22, 11, 90]
print("Original:", data)
print("Bubble sort:", bubble_sort(data))
print("Insertion sort:", insertion_sort(data))
print("Merge sort:", merge_sort(data))
print("Quick sort:", quick_sort(data))
# Output:
# Original: [64, 34, 25, 12, 22, 11, 90]
# Bubble sort: [11, 12, 22, 25, 34, 64, 90]
# Insertion sort: [11, 12, 22, 25, 34, 64, 90]
# Merge sort: [11, 12, 22, 25, 34, 64, 90]
# Quick sort: [11, 12, 22, 25, 34, 64, 90]

Chapter 11

Recursion & Backtracking

Recursion is when a function calls itself to solve a smaller version of the same problem. It feels strange at first, but it is a natural way to handle problems that have a repeating shape inside themselves. The secret is the base case: a condition where the function stops calling itself and just returns a simple answer. Without a base case, recursion would run forever, just like a loop without an exit condition.

Think of factorial. 5! means 5 × 4 × 3 × 2 × 1. But 5! is also 5 × 4!, and 4! is 4 × 3!, and so on, until 0! = 1. The function asks itself a smaller question each time, then multiplies the answers on the way back up.

Backtracking is recursion with a safety net. You try a choice, explore where it leads, and if it doesn't work, you undo the choice and try the next one. It is how you solve puzzles like Sudoku, generate all permutations of a word, or place queens on a chessboard so none attack each other. The "undo" is what makes it backtracking: you explore a branch, and if it fails, you back out and continue from where you left off.

Factorial, Fibonacci, and permutations

The first function computes factorial, the second computes Fibonacci the naive way (notice it is slow for large n), and the third generates all rearrangements of a string. Permutations is a great example of backtracking: we pick each letter, recursively permute the rest, and combine them. 

"""Recursion and backtracking demos.
Run: python recursion_demo.py
"""

def factorial(n):
    """n! = n * (n-1)! ; base case 0! = 1"""
    if n == 0:
        return 1
    return n * factorial(n - 1)

def fibonacci(n):
    """Naive recursive Fibonacci — O(2^n). Use DP for speed."""
    if n <= 1:
        return n
    return fibonacci(n - 1) + fibonacci(n - 2)

def permutations(s):
    """All rearrangements of a string via backtracking."""
    if len(s) <= 1:
        return [s]
    result = []
    for i, ch in enumerate(s):
        rest = s[:i] + s[i+1:]
        for perm in permutations(rest):
            result.append(ch + perm)
    return result

print("Factorial of 5:", factorial(5))      # 120
print("Fibonacci of 8:", fibonacci(8))      # 21
print("Permutations of 'abc':", permutations("abc"))
# ['abc', 'acb', 'bac', 'bca', 'cab', 'cba']
# Output:
# Factorial of 5: 120
# Fibonacci of 8: 21
# Permutations of 'abc': ['abc', 'acb', 'bac', 'bca', 'cab', 'cba']

Chapter 12

Dynamic Programming

Dynamic programming (DP) is a technique for solving problems that contain the same smaller problem many times. Instead of recomputing the same thing over and over, we compute each subproblem once and save the answer. This simple change can turn a program that takes years into one that finishes in a second.

Imagine you are climbing a staircase with n steps, and you can take 1 or 2 steps at a time. How many ways can you reach the top? The answer for step n depends only on the answers for steps n-1 and n-2. A naive recursive solution would ask for the same step again and again. DP remembers each answer so the work becomes linear.

There are two common styles. Memoization is top-down: write the recursive solution first, then cache results. Tabulation is bottom-up: build a table from the smallest cases upward, using previous entries to fill new ones. Both avoid the explosion of repeated work. DP is behind spell-checkers, DNA matching, shortest-path algorithms, game AI, and much more.

Fibonacci: naive vs memoized vs tabulated

This program computes the 40th Fibonacci number three ways. The naive recursion takes a noticeable amount of time because it recomputes the same values millions of times. The memoized and tabulated versions are nearly instant. All three return the same answer: 102,334,155. 

"""Dynamic programming: Fibonacci three ways.
Run: python dp_demo.py
"""

# Naive recursion — O(2^n), slow
def fib_naive(n):
    if n <= 1:
        return n
    return fib_naive(n - 1) + fib_naive(n - 2)

# Memoization (top-down) — O(n)
from functools import lru_cache
@lru_cache(maxsize=None)
def fib_memo(n):
    if n <= 1:
        return n
    return fib_memo(n - 1) + fib_memo(n - 2)

# Tabulation (bottom-up) — O(n) time, O(n) space
def fib_tab(n):
    if n <= 1:
        return n
    dp = [0] * (n + 1)
    dp[1] = 1
    for i in range(2, n + 1):
        dp[i] = dp[i - 1] + dp[i - 2]
    return dp[n]

n = 40
print(f"fib_naive({n}) =", fib_naive(n))      # slow but correct
print(f"fib_memo({n})  =", fib_memo(n))       # instant
print(f"fib_tab({n})   =", fib_tab(n))        # instant
# All print: 102334155
# Output:
# fib_naive(40) = 102334155
# fib_memo(40)  = 102334155
# fib_tab(40)   = 102334155

Chapter 13

Greedy Algorithms

A greedy algorithm always makes the choice that looks best right now, without worrying about the future. It is like hiking and always taking the steepest upward path, hoping it leads to the highest peak. Sometimes it works perfectly; sometimes it gets stuck on a small hill while the real mountain is just one valley away.

Greedy algorithms are attractive because they are simple and fast. At every step you pick the locally best option and move on — usually O(n log n) if you need to sort first, or O(n) otherwise. They work when the problem has the greedy-choice property: a locally best choice is also part of a globally best answer. Canonical coin systems, like US coins, have this property, so greedy coin change always gives the fewest coins.

But beware: greedy is not always correct. If the coin system is weird — say coins of 1, 3, and 4 — greedy might pick 4 + 1 + 1 = 6 for an amount of 6, while the optimal answer is 3 + 3 = 2 coins. When greedy fails, you usually need dynamic programming or another exhaustive method. The skill is learning to recognize when greedy is safe.

Coin change (greedy, canonical coins)

This classic example uses US coins [1, 5, 10, 25]. The greedy rule is simple: use as many quarters as possible, then dimes, then nickels, then pennies. For 93¢, it takes 3 quarters (75¢), 1 dime (10¢), 1 nickel (5¢), and 3 pennies (3¢), totaling 8 coins. Try changing the coin list to [1, 3, 4] and amount to 6 to see where greedy fails. 

"""Greedy coin change: fewest coins for canonical denominations.
Run: python greedy_demo.py
"""

def coin_change_greedy(amount, coins):
    """Return dict {coin: count} using largest coins first."""
    coins = sorted(coins, reverse=True)
    result = {}
    remaining = amount
    for coin in coins:
        count = remaining // coin
        if count:
            result[coin] = count
            remaining -= count * coin
    if remaining != 0:
        return None  # cannot make exact change with these coins
    return result

amount = 93
coins = [1, 5, 10, 25]  # US coins (canonical: greedy works)
change = coin_change_greedy(amount, coins)
print(f"Amount: {amount}")
print(f"Coins:  {coins}")
print(f"Change: {change}")
print(f"Total coins: {sum(change.values())}")
# Output:
# Amount: 93
# Coins:  [1, 5, 10, 25]
# Change: {25: 3, 10: 1, 5: 1, 1: 3}
# Total coins: 8  (3*25 + 1*10 + 1*5 + 3*1 = 93)

Capstone Project

Build a "Route & Task Planner"

This capstone combines everything you have learned into one real-world program: a Route & Task Planner. Imagine you are running a delivery service. You have a map of cities connected by roads, a list of urgent tasks to complete, and a fast way to look up any city by name. DSA gives you the perfect tools for each of these jobs.

First, a graph stores cities as nodes and roads as weighted edges. This lets you ask, "Which cities can I reach from here?" using BFS or DFS, and later "What is the shortest driving route?" using Dijkstra's algorithm. Second, a min-heap priority queue schedules tasks so the most urgent one is always handled first. Third, a hash table maps city names to their graph data, giving O(1) lookups by name instead of searching through lists.

The project is split into five phases so you can build it piece by piece: build the graph, add the scheduler, add fast city lookup, wire them together in a simple menu, and finally polish the output. By the end, you will have a single runnable Python program that uses at least four of the data structures and algorithms from this tutorial.

"""Route & Task Planner capstone.
Graph + priority queue + hash table. Run: python planner.py
"""

from collections import deque
import heapq

# --- Graph: cities and roads with distances ---
class CityGraph:
    def __init__(self):
        self.adj = {}   # city -> list of (neighbor, distance)

    def add_road(self, a, b, dist):
        self.adj.setdefault(a, []).append((b, dist))
        self.adj.setdefault(b, []).append((a, dist))

    def bfs_reachable(self, start):
        """Cities reachable from start (unweighted reachability)."""
        visited = {start}
        queue = deque([start])
        while queue:
            city = queue.popleft()
            for neighbor, _ in self.adj.get(city, []):
                if neighbor not in visited:
                    visited.add(neighbor)
                    queue.append(neighbor)
        return sorted(visited)

    def dijkstra(self, start, goal):
        """Shortest path by distance using a min-heap."""
        dist = {start: 0}
        prev = {start: None}
        heap = [(0, start)]
        while heap:
            d, city = heapq.heappop(heap)
            if city == goal:
                break
            if d > dist.get(city, float('inf')):
                continue
            for neighbor, w in self.adj.get(city, []):
                nd = d + w
                if nd < dist.get(neighbor, float('inf')):
                    dist[neighbor] = nd
                    prev[neighbor] = city
                    heapq.heappush(heap, (nd, neighbor))
        # Reconstruct path
        path = []
        at = goal
        while at is not None:
            path.append(at)
            at = prev.get(at)
        path.reverse()
        return dist.get(goal, float('inf')), path if path and path[0] == start else []

# --- Task scheduler: min-heap by priority ---
class TaskScheduler:
    def __init__(self):
        self.heap = []
        self.counter = 0  # tie-breaker so equal priorities stay ordered

    def add(self, task, priority):
        heapq.heappush(self.heap, (priority, self.counter, task))
        self.counter += 1

    def next_task(self):
        if not self.heap:
            return None
        _, _, task = heapq.heappop(self.heap)
        return task

    def __str__(self):
        return ", ".join(t for _, _, t in sorted(self.heap)) or "none"

# --- Interactive planner ---
def main():
    graph = CityGraph()
    for a, b, d in [
        ("NYC", "Philly", 95), ("Philly", "DC", 140),
        ("DC", "Richmond", 110), ("NYC", "Boston", 215),
        ("Boston", "Providence", 50), ("Providence", "Hartford", 100),
        ("Hartford", "NYC", 120),
    ]:
        graph.add_road(a, b, d)

    scheduler = TaskScheduler()

    print("=== Route & Task Planner ===\n")
    while True:
        print("1. Add a task")
        print("2. Show next task")
        print("3. Find shortest route between cities")
        print("4. List reachable cities from a city")
        print("5. Exit")
        choice = input("\nChoose (1-5): ").strip()

        if choice == "1":
            task = input("Task description: ").strip()
            try:
                priority = int(input("Priority (1=highest, 5=lowest): "))
            except ValueError:
                priority = 3
            scheduler.add(task, priority)
            print(f"  ✅ Added: '{task}' (priority {priority})\n")
        elif choice == "2":
            task = scheduler.next_task()
            if task:
                print(f"  ▶ Next: {task}\n")
            else:
                print("  No tasks scheduled.\n")
        elif choice == "3":
            start = input("From city: ").strip().upper()
            goal = input("To city: ").strip().upper()
            dist, path = graph.dijkstra(start, goal)
            if path:
                print(f"  Shortest route {start} -> {goal}: {' -> '.join(path)} ({dist} miles)\n")
            else:
                print(f"  No route from {start} to {goal}.\n")
        elif choice == "4":
            city = input("City: ").strip().upper()
            reachable = graph.bfs_reachable(city)
            print(f"  From {city}, reachable: {', '.join(reachable)}\n")
        elif choice == "5":
            print("\nGoodbye! 🎓\n")
            break
        else:
            print("  Invalid choice.\n")

if __name__ == "__main__":
    main()
