Chapter 2

Relational Databases

Relational databases remain the default for structured transactional workloads. PostgreSQL and MySQL are open-source, proven choices. They enforce schemas, support joins, and provide ACID guarantees. See SQL & Databases and Database Optimization for deeper coverage.

PostgreSQL

  • Advanced indexing, JSON support, CTEs, window functions.
  • Excellent extensibility and open-source community.
  • Strong choice for OLTP and light analytics.

MySQL / MariaDB

  • Widely deployed in web applications.
  • Good replication tooling and managed options.
  • Common in LAMP/LEMP stacks.

Chapter 3

NoSQL Databases

NoSQL databases relax the rigid relational model to scale horizontally, handle flexible schemas, or optimize specific access patterns. They are grouped into key-value, document, column-family, and graph stores.

Key-value & wide-column

  • Redis: in-memory key-value store. See Redis & Caching.
  • DynamoDB, Cassandra, HBase, Bigtable: wide-column stores for massive scale.

Document & graph

  • MongoDB, CouchDB: flexible JSON documents. See MongoDB & NoSQL.
  • Neo4j, Amazon Neptune: graph databases for relationships. See Graph Databases.

Chapter 4

CAP Theorem

The CAP theorem states that a distributed data store can only guarantee two of three properties during a partition: Consistency, Availability, and Partition tolerance. Since partitions are unavoidable, the real choice is between CP and AP systems.

CAP trade-off triangle

CP systems

Favor consistency over availability during a partition. Examples: HBase, Redis Cluster, etcd, ZooKeeper.

AP systems

Favor availability and accept eventual consistency. Examples: Cassandra, DynamoDB, CouchDB.

Practical note

Most distributed systems tune the trade-off per operation. For example, Cassandra lets you choose consistency levels per query (ONE, QUORUM, ALL).

Chapter 5

Lake, Warehouse, Mart, Mesh, Fabric, Hub

Modern organizations store data at multiple layers. Each layer solves a different problem, from cheap raw storage to curated departmental datasets.

Storage layers

  • Data lake: cheap raw storage in S3/GCS/Blob (JSON, Parquet, CSV).
  • Data warehouse: structured, query-optimized store for analytics.
  • Data mart: department-specific subset of a warehouse.

Architectural styles

  • Data mesh: domain-oriented, decentralized data ownership.
  • Data fabric: unified metadata and integration layer across silos.
  • Data hub: central exchange that connects producers and consumers.

Comparison

Concept Best for
Data lake Cheap storage of raw, diverse data
Data warehouse Fast SQL analytics on curated data
Data mart Departmental reporting (sales, finance)
Data mesh Large orgs with autonomous domains
Data fabric Unified discovery across distributed systems

Chapter 6

Lakehouse

A lakehouse merges the low-cost storage of a data lake with the transactional reliability and performance of a warehouse. Open table formats like Delta Lake, Apache Iceberg, and Apache Hudi make this possible.

Why lakehouse?

  • Store raw and curated data on cheap object storage.
  • Support ACID transactions, time travel, and schema evolution.
  • Run both BI and ML workloads on the same data.

Platforms

  • Databricks: Delta Lake + Spark.
  • Snowflake: managed warehouse with external table support.
  • AWS Glue + Athena: query Iceberg tables on S3.
# Save as delta_setup.py, then run with uv
cat << 'EOF' > delta_setup.py
from pyspark.sql import SparkSession

spark = SparkSession.builder \
    .appName("DeltaSetup") \
    .config("spark.sql.extensions", "io.delta.sql.DeltaSparkSessionExtension") \
    .getOrCreate()

spark.sql("""
  CREATE TABLE IF NOT EXISTS bronze.events (
    event_id STRING,
    user_id STRING,
    event_type STRING,
    page STRING,
    ts TIMESTAMP
  ) USING DELTA
  LOCATION 's3a://my-lake/bronze/events'
""")

# Time travel: query table as of a previous version
path = "s3a://my-lake/bronze/events"
spark.read.format("delta").option("versionAsOf", 5).load(path).show()
EOF

uv run --with delta-spark delta_setup.py

Chapter 7

Indexing & Choosing Technologies

Indexes speed up reads at the cost of write overhead. Choosing the right storage is about matching access patterns, scale, consistency needs, and team skills.

Decision framework

  • Structured transactions: PostgreSQL or MySQL.
  • Flexible documents at scale: MongoDB, CouchDB.
  • Massive wide-column/time series: Cassandra, Bigtable, DynamoDB.
  • Graph relationships: Neo4j, Neptune.
  • Ad-hoc analytics: Snowflake, BigQuery, Redshift.
  • Unified lake + warehouse: Databricks, Glue + Athena.
-- Typical indexing for an event analytics warehouse
CREATE INDEX idx_events_user_id ON events(user_id);
CREATE INDEX idx_events_event_type_ts ON events(event_type, event_ts);
CREATE INDEX idx_events_page_ts ON events(page, event_ts);

-- Composite covering index for funnel queries
CREATE INDEX idx_events_funnel ON events(event_type, page, event_ts)
INCLUDE (user_id, session_id);

Remember

No database does everything well. Use the best tool for each workload and connect them with pipelines.

Chapter 8

Capstone: SaaS Event Analytics Warehouse

1. What is this project?

You will design a data warehouse for a SaaS product that captures clickstream events. The project covers source schemas, a star schema, storage layer choices, and analytical queries.

2. What it covers?

  • Define event sources and business questions.
  • Design OLTP source schema and OLAP star schema.
  • Choose storage: Postgres for OLTP, S3 data lake, warehouse layer.
  • Implement fact/dimension tables in SQL.
  • Write analytical queries and explain technology choices.

3. How it is done?

Start with the OLTP event table, then model dimensions and a fact table for analytics. Use S3 as a raw landing zone and Postgres/SQLite for the curated warehouse.

-- OLTP source table (application database)
CREATE TABLE app_events (
    event_id UUID PRIMARY KEY,
    user_id INT NOT NULL,
    event_type VARCHAR(50) NOT NULL,
    page VARCHAR(200),
    session_id VARCHAR(100),
    event_ts TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- OLAP dimensions
CREATE TABLE dim_user (
    user_key SERIAL PRIMARY KEY,
    user_id INT NOT NULL,
    email_domain VARCHAR(100),
    signup_date DATE,
    plan VARCHAR(50),
    valid_from DATE NOT NULL,
    valid_to DATE,
    is_current BOOLEAN DEFAULT TRUE
);

CREATE TABLE dim_date (
    date_key INT PRIMARY KEY,
    full_date DATE NOT NULL,
    year INT,
    month INT,
    day_of_week INT
);

-- OLAP fact table
CREATE TABLE fact_events (
    event_key BIGSERIAL PRIMARY KEY,
    event_id UUID NOT NULL,
    user_key INT REFERENCES dim_user(user_key),
    date_key INT REFERENCES dim_date(date_key),
    event_type VARCHAR(50),
    page VARCHAR(200),
    session_id VARCHAR(100)
);
-- Daily active users (DAU)
SELECT d.full_date, COUNT(DISTINCT f.user_key) AS dau
FROM fact_events f
JOIN dim_date d ON d.date_key = f.date_key
GROUP BY d.full_date
ORDER BY d.full_date;

-- Top pages by event count this month
SELECT f.page, COUNT(*) AS views
FROM fact_events f
JOIN dim_date d ON d.date_key = f.date_key
WHERE f.event_type = 'page_view'
  AND d.year = 2024 AND d.month = 9
GROUP BY f.page
ORDER BY views DESC
LIMIT 10;
# Conceptual storage architecture
layers:
  raw:
    store: s3://saas-events/raw/{year}/{month}/{day}/
    format: JSON Lines
  bronze:
    store: s3://saas-events/bronze/
    format: Parquet
  warehouse:
    store: Postgres / Snowflake
    schema: star_schema
  marts:
    product: fact_events + dim_user + dim_date
    marketing: acquisition_funnel

4. What did we learn from this capstone project?

  • OLTP schemas optimize writes; OLAP schemas optimize analytical reads.
  • A star schema with dimensions and facts makes reporting straightforward.
  • Layered storage (lake + warehouse + mart) balances cost, flexibility, and performance.
  • Indexes should match query predicates for fast dashboards.

5. How can I enhance this project in the future?

  • Partition the fact table by date and load it into BigQuery or Snowflake.
  • Add sessionization logic to build a funnel analysis.
  • Convert raw JSON to Parquet using Python or Spark.
  • Add a DataOps tutorial-style dashboard with Streamlit or a BI tool.
  • Model a data mesh by splitting user-domain and event-domain ownership.
